# Известные проблемы и ограничения — Коммерческий проект

## Открытые (осознанно принятые риски MVP)

1. **S_RU совмещает роли** (relay-нода + панель + БД + бот)
   Риск: при аварии/атаке возможна одновременная деградация всех функций
   План: разнести на отдельный S3 после начала продаж и роста нагрузки

2. **S2 ограничен по RAM (709 MiB)**, несёт и Pi-hole (домашний), и EU-exit (коммерция)
   Риск: при росте коммерческого трафика — нехватка памяти, может задеть Pi-hole
   План: мониторить, при необходимости — отдельный EU-VPS под коммерцию

3. **Whitelist-блокировка (default-deny)** — гипотетический жёсткий сценарий,
   при котором блокируется весь трафик кроме явно разрешённого
   Статус: НЕ решается никакой архитектурой, если затронет сами датацентры РФ
   Митигация: RU-нода как единственная точка входа снижает риск для
   частичного whitelist (блокировка только иностранных IP)

4. **Soft-limit на устройства** — не enforced технически, только количество
   выданных учётных данных на тариф
   Риск: клиент может использовать один конфиг на большем числе устройств,
   чем оплатил
   План: пересмотреть при масштабировании, если увидим злоупотребления

5. **Антифрод триала неполный** — защита по tg_id + телефон,
   обход возможен через новый номер + новый аккаунт
   Принято как риск MVP

## Зависимости от домашней инфраструктуры (НЕ создавать!)

Явное правило: коммерческий проект НЕ ДОЛЖЕН зависеть от домашних
S1/S2 сервисов, кроме:
- Использования S2 как EU-exit ноды (изолированная docker-сеть/iptables)
- Использования домашнего хаба S1 для VPN-доступа админа к панели
  (S_RU как клиент, аналогично Petr/Vova)

Любые другие точки пересечения — АРХИТЕКТУРНАЯ ОШИБКА, требует пересмотра.
