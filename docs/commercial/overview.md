## Схема маршрутизации трафика клиентов (geo-split)

```
Клиент (v2rayNG/Hiddify/Shadowrocket/Streisand)
  │
  ├── RU домены/IP (geosite:ru, geoip:ru) → outbound "direct"
  │     (напрямую, без VPN, обычный российский IP клиента)
  │
  └── всё остальное → outbound "chain"
        Клиент → S_RU (Reality inbound) → relay → S2 (EU exit) → интернет
```

Обоснование:
- Устойчивость к DPI-блокировке по сигнатурам → протокол Reality (маскировка под TLS)
- Устойчивость к whitelist-блокировке иностранных IP → единственная точка входа
  с территории РФ это S_RU, EU используется только вторым скрытым хопом
- RU-сервисы (банки, госуслуги) видят настоящий российский IP клиента

## Протокол и клиенты

- Движок: Xray-core через Marzban (панель + API + мультинода)
- Основной протокол: VLESS + Reality
- Резервный протокол: Shadowsocks-2022 (тот же Marzban, доп. inbound)
- Клиенты Android: v2rayNG (приоритет), Hiddify Next, NekoBox
- Клиенты iOS: Shadowrocket (приоритет), Streisand

## Домены

РЕШЕНИЕ: домены не используются.
- VPN-инбаунды (Reality) — только по IP, маскировка под чужой SNI, домен не нужен
  и даже вреден (легче банить по SNI, чем по голому IP)
- Веб-панель Marzban — self-signed сертификат, доступ ТОЛЬКО из VPN
  (S_RU подключается как клиент к домашнему хабу S1, панель на internal IP)
- Telegram-бот — long polling, без webhook, HTTPS/домен не требуется

## Известные риски / ограничения (осознанно принятые для MVP)

1. S_RU временно совмещает relay-ноду и панель+бот+БД — при аварии/атаке
   возможна деградация обеих функций одновременно. Разнести после роста нагрузки.
2. S2 (EU-exit) 709 MiB RAM, уже несёт Pi-hole — риск при росте коммерческой нагрузки.
3. Whitelist-блокировка в максимально жёстком варианте (только гос.сервисы) —
   не решается никакой архитектурой, риск вне контроля проекта.
4. Лимит устройств — soft (по количеству выданных конфигов на тариф), не enforced технически.
5. Антифрод триала — Telegram ID + номер телефона, обход через новый номер+аккаунт
   технически возможен, принимается как риск MVP.

## Прогресс на 16.09.2026 (конец сессии)

### Важное открытие про диагностику Marzban API

Эндпоинт /api/core/config, ВОЗМОЖНО, возвращает шаблон конфига с диска
(с пустым inbounds[].settings.clients), а НЕ реальный runtime-конфиг
ядра Xray с фактически подключенными пользователями. Это не подтверждено
на 100%, но объясняет, почему при "Clients: []" в ответе API клиент
Hiddify реально подключался и передавал трафик.
ВЫВОД: не полагаться на этот эндпоинт для диагностики в будущем,
проверять реальное подключение клиентом напрямую.

### Транспортный relay-канал S_RU -> S2: РАБОТАЕТ

Клиент Hiddify успешно подключился к финальному конфигу
(с outbound to-eu, БЕЗ секции routing - см. ниже про баг).

### ⚠️ НЕРЕШЁННЫЙ ВОПРОС: секция routing ломает работу конфига

При добавлении секции "routing" (geoip:ru -> DIRECT, остальное -> to-eu)
в xray_config.json клиент получал timeout при подключении.
После УДАЛЕНИЯ секции routing (оставили только inbounds + outbounds,
outbound to-eu присутствует) - подключение снова заработало.

ПРИЧИНА НЕ УСТАНОВЛЕНА. Гипотезы для проверки в следующей сессии:
1. Неверный синтаксис routing-правил для версии Xray-core 24.12.31
2. Marzban может сам генерировать свою секцию routing и конфликтовать с ручной
3. Возможно нужен другой формат (balancers вместо прямых outboundTag правил)
4. Порядок правил в routing.rules может иметь значение

ТЕКУЩЕЕ СОСТОЯНИЕ: geo-split НЕ РАБОТАЕТ, весь трафик (кроме локального
подключения) идёт предположительно БЕЗ разделения RU/EU - требует
проверки, куда реально роутится трафик сейчас (см. TODO ниже).
