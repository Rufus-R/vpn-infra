## Суть решения (зафиксировано 25.09.2026, подтверждено 26.09.2026)

Переход с Marzban на **3x-ui** (`MHSanaei/3x-ui`, mainline-проект).
Причины:
- Единая панель для VLESS+Reality и AmneziaWG (резервный канал) с общей
  базой пользователей
- Встроенная поддержка multi-node (панель управляет удалёнными нодами)
- Marzban показал жёсткое ограничение: внешний доступ к веб-панели
  невозможен без публично доверенного TLS-сертификата (self-signed
  принудительно отклоняется кодом самого Marzban, `UVICORN_HOST`
  сбрасывается на `127.0.0.1`)

⚠️ **Риск, принятый осознанно**: README самого 3x-ui заявляет проект как
предназначенный для "personal learning" и прямо не рекомендует
использовать в продакшене. Решение использовать его в коммерческом
проекте принято, несмотря на это предупреждение — пересмотреть при
первых признаках нестабильности.

- Локальная подписка отключена на S_RU и S2 (была включена по умолчанию,

- Master-панель (`25305` на Panel) дополнена explicit ACCEPT для
  доверенных IP (`194.55.236.229`, `77.105.161.151`, `31.77.169.67`,
  `46.32.82.242`) — общее правило `Anywhere` на тот момент не было удалено
  (удалено 02.10.2026, см. `system-state.md`)

### Обнаружена, детально продиагностирована, но НЕ РЕШЕНА критическая проблема

**Симптом**: реальные VPN-клиенты (и v2rayNG, и Hiddify — идентичный
результат, что исключает клиент-специфичную причину) подключаются к
`S_RU:443` (VLESS+Reality), TLS/Reality handshake на клиенте проходит
успешно, трафик генерируется и уходит в `tun`-интерфейс, но интернет не
работает: `context deadline exceeded` на внутреннем latency-тесте
клиента (`generate_204`).

**Последовательно проверено и исключено**:
1. Firewall S2 (сегодняшнее изменение политики) — НЕ причина:
   OpenVPN-канал S1↔S2 работает нормально, relay-порт 10001 принимает
   TCP-соединения, счётчики пакетов на ACCEPT-правиле растут во время
   теста
2. MTU/фрагментация на канале S_RU↔S2 — НЕ причина: DF-ping с payload
   1400 байт проходит 0% потерь между серверами
3. Certificate pinning (`pinnedPeerCertSha256` в outbound S_RU) — НЕ
   причина: sha256-отпечаток реального сертификата S2
   (`/etc/x-ui/certs/server.crt`) точно совпадает с захардкоженным pin
4. TLS-уровень S_RU→S2:10001 — исправен: `openssl s_client` с S_RU до
   S2:10001 успешно получает сертификат (self-signed warning ожидаем)
5. Reality keypair — совпадает: `xray x25519 -i <privateKey сервера>`
   на S_RU выдаёт publicKey, идентичный тому, что зашит в текущем
   клиентском профиле (обновлён оператором в этой же сессии через
   `netru.ru.net:2096`)
6. `shortId` клиента (`<см. менеджер паролей>`) присутствует в списке
   разрешённых на сервере; UUID клиента совпадает на обеих сторонах

**Ключевая улика (tcpdump)**: во время попытки подключения клиента
запущен одновременный захват пакетов на S2 (фильтр `host 31.77.169.67
and port 10001`) и на S_RU (фильтр `port 443 or (host 77.105.161.151
and port 10001)`). Результат: **на relay-порт 10001 не пришло ни
одного пакета** за всё время теста. На S_RU:443 видны короткие TCP-сессии
от IP клиента с паттерном `seq=1, ack=1389` и немедленным `FIN` —
похоже на поведение Reality, не распознающего сессию клиента как
легитимную и отвечающего от имени сайта-прикрытия (`www.cloudflare.com`
в `serverNames`/`target`), вместо проксирования VLESS-трафика дальше.

**Вывод**: обрыв происходит **на самом S_RU**, до relay-канала к S2.
Несмотря на то, что все параметры Reality (ключи, shortId, SNI)
формально совпадают, хендшейк не считается сервером валидным для
проксирования.

## Инцидент 30.09.2026 (вечер) — неудачная попытка geo-split, сервис временно лежал

### Что произошло
Попытка добавить geo-split routing на S_RU (`geosite:ru`/`geoip:ru` →
`direct`, `domainStrategy: IPIfNonMatch`) через прямую правку
`xrayTemplateConfig` в `/etc/x-ui/x-ui.db` привела к падению Xray:

```
XRAY: Failed to start: ... invalid field rule > common/geodata:
illegal domain rule: geosite:ru > common/geodata: failed to check
code RU from geosite.dat > EOF
```

Xray ушёл в crash-loop, **порт 443 не слушался** — реальные клиенты
были без VPN в течение ~10 минут во время диагностики и отката.

### Причина падения Xray (расследовано 01.10.2026: в `geosite.dat` нет категории `RU`, файл не повреждён — см. «Сессия 01.10.2026»)
Файл `/usr/local/x-ui/bin/geosite.dat` (11 МБ, обновлён 16.09.2026; уточнено 01.10: 17 МБ — это `geoip.dat`)
не проходит валидацию категории `RU` парсером Xray-core v26.6.27—
похоже на повреждённый или неполный файл geo-базы. `geoip:ru`
изолированно не тестировался (откат сделан раньше, чем дошли до
раздельного теста) — **неизвестно, работает ли geoip:ru отдельно**.

### Важная находка: откат SQLite-базы через `cp` НЕ РАБОТАЕТ, если сервис жив
Первая попытка отката (`cp` бэкапа поверх `/etc/x-ui/x-ui.db` +
`systemctl restart x-ui`) **не сработала** — после restart в БД
снова оказались 5 "плохих" правил вместо 3 исходных, хотя `cp`
выполнился успешно. Причина: SQLite в WAL-режиме держит
несинхронизированные изменения в отдельных файлах `x-ui.db-wal` /
`x-ui.db-shm` рядом с основным `.db`. Обычный `cp` подменяет только
основной файл; при следующем запуске SQLite находит "свежий" WAL и
реплеит его поверх восстановленного файла, **возвращая старые (плохие)
данные обратно**.

**Правильный порядок отката `x-ui.db`** (зафиксировать как процедуру
на будущее):
```bash
systemctl stop x-ui                    # сервис ПОЛНОСТЬЮ остановлен
rm -f /etc/x-ui/x-ui.db \
      /etc/x-ui/x-ui.db-wal \
      /etc/x-ui/x-ui.db-shm            # удалить И основной файл, И WAL/SHM
cp /root/x-ui.db.backup-<TIMESTAMP> /etc/x-ui/x-ui.db
systemctl start x-ui
```
Простой `systemctl restart` (без `stop`) тоже недостаточен — нужен
именно raw `stop` перед удалением файлов, чтобы процесс гарантированно
закрыл файловые хендлы перед заменой.
