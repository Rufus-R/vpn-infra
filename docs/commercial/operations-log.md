## Суть решения (зафиксировано 25.09.2026, подтверждено 26.09.2026)

Переход с Marzban на **3x-ui** (`MHSanaei/3x-ui`, mainline-проект).
Причины:
- Единая панель для VLESS+Reality и AmneziaWG (резервный канал) с общей
  базой пользователей
- Встроенная поддержка multi-node (панель управляет удалёнными нодами)
- Marzban показал жёсткое ограничение: внешний доступ к веб-панели
  невозможен без публично доверенного TLS-сертификата (self-signed
  принудительно отклоняется кодом самого Marzban, `UVICORN_HOST`
  сбрасывается на `127.0.0.1`)

⚠️ **Риск, принятый осознанно**: README самого 3x-ui заявляет проект как
предназначенный для "personal learning" и прямо не рекомендует
использовать в продакшене. Решение использовать его в коммерческом
проекте принято, несмотря на это предупреждение — пересмотреть при
первых признаках нестабильности.

## Сессия 10-11.10.2026 — access-лог Xray, согласие на ПДн, юридические документы

### Находка: access-лог Xray писал данные клиентов несмотря на `loglevel:"none"`

Обнаружено, что `loglevel:"none"` в шаблоне Xray НЕ отключает access-лог — это разные
параметры. Лог на S_RU и S2 писал в `/var/log/x-ui/access.log` IP клиента, домен назначения
и email клиента, несмотря на кажущееся «логи выключены» в UI. Исправлено: `"access":"none"`
добавлен в шаблон Xray на обоих серверах (подтверждено в БД — сохраняется постоянно,
переживает полный рестарт x-ui). Старые файлы логов на S_RU и S2 очищены.

### Юридические документы: публичная оферта и политика конфиденциальности переработаны

Текст `oferta.md`/`privacy-policy.md` (вне git, `/root/commercial-legal/` на S1) существенно
переработан по итогам ревизии на соответствие фактической реализации (ряд формулировок,
предложенных внешним консультантом, не совпадал с кодом — см. правило из `session-start.md`,
раздел 6, про верификацию внешних гипотез перед использованием):

- **Трафик (Оферта п.5.3):** исходная формулировка «не ведётся учёт объёма трафика» была
  фактически неверна — трафик технически учитывается (`totalGB`/`usedTraffic` в 3x-ui,
  отображается через `Subscription-Userinfo` на странице подписки). Исправлено: «не ведётся
  журнал посещаемых ресурсов», при этом «объём трафика технически учитывается и
  отображается», отдельно зафиксировано, что текущие тарифы безлимитны.
- **IP-адреса устройств (Политика, раздел 2):** исходный текст утверждал «IP-адреса не
  обрабатываются» — проверка схемы `x-ui.db` на Panel опровергла это: таблицы
  `inbound_client_ips` (UNIQUE по `client_email`) и `node_client_ips` хранят **текущий**
  IP клиента для контроля `limit_ip` (без истории — одна строка на клиента, значение
  перезаписывается). Политика исправлена: IP-адреса добавлены в состав обрабатываемых
  данных с пояснением об отсутствии журнала/истории.
- **Хостинг-провайдеры (Политика, раздел 4):** добавлена категория получателя данных
  «хостинг-провайдеры (операторы дата-центров) ... на территории РФ» — решение оператора:
  без указания конкретных названий компаний (whois показал разных юрлиц для разных

  зоны. Очищено вручную до единственной записи `0 issue "letsencrypt.org"` — соответствует

- SPF (`v=spf1 include:_spf.spaceweb.ru -all`) и DMARC (`p=none`) перенесены без изменений —

## Сессия 14.10.2026 — отказ от ЮKassa в пользу Robokassa, тестовый платёж пройден

### Смена провайдера: ЮKassa → Robokassa

ЮKassa (shopId `1483176`, API-ключ получен) оказалась неприменима в исходном виде: услуга
«Чеки от ЮKassa» подключается только для ИП-неНПД/юрлиц, для самозанятых (НПД) чек всё
равно пришлось бы формировать вручную через «Мой налог» после каждого платежа — то есть
ровно та проблема, ради которой 11.10.2026 полностью исключили fallback-оплату, не решалась
переходом на ЮKassa. Оператор принял решение переехать на **Robokassa**, у которой есть
отдельное решение **«Робочеки СМЗ»** — автоматическое формирование НПД-чека через интеграцию
с «Мой налог», без ручного шага.

Полная техническая спецификация (алгоритм подписи, структура `Receipt`, блокеры активации) —
см. `bot.md`, раздел «Платёжный провайдер: Robokassa».

### Исследование через внешнего поискового агента + верификация письмом техподдержки

Первый запрос внешнему агенту дал частично неполную картину: официальная документация
`docs.robokassa.ru` описывает `Receipt` только для 54-ФЗ-фискализации (ИП/юрлица), раздел
`sno` не содержит режима НПД — агент явно пометил это как неподтверждённый пробел (правило
`session-start.md`, раздел 6: не использовать гипотезы внешнего агента без верификации).
Пробел закрыт прямым письмом техподдержки Robokassa: для самозанятого/ИП на НПД нужно
передавать только обязательные поля `Receipt` (`name`, `quantity`, `sum`, `tax=none`), без
`sno`/`payment_method`/`payment_object` — передача несуществующих значений ломает чек.

### Тестовый платёж — пройден дважды (MD5 и SHA256)

Собрана тестовая ссылка оплаты вручную Python-скриптом (без сетевого вызова — только
построение URL по документированному алгоритму). Критичная деталь, подтверждённая
техподдержкой: `Receipt` при инициации платежа участвует в подписи URL-кодированным один
раз, а в самом GET-параметре итоговой ссылки — закодирован дважды. Обе тестовые ссылки
(`IsTest=1`, алгоритмы MD5 и затем SHA256) открылись без ошибки подписи, при раскрытии
деталей заказа на странице Robokassa отображён верный состав («Тестовый тариф Штиль»,
1,00 ₽ × 1) — ровно тот критерий корректной передачи номенклатуры, который указала
техподдержка. Решено использовать SHA256 в проде (MD5 признан избыточно устаревшим для
новой интеграции, хотя для данной схемы подписи практическая атака неприменима — решение
по общей дисциплине безопасности проекта).

### Находка: Robokassa сама собирает email покупателя для чека

На странице оплаты Robokassa есть обязательное поле «Email для чека» — заполняется
покупателем напрямую у Robokassa, не передаётся и не хранится ботом. Снимает вопрос о
необходимости сбора email в сценарии оплаты (не расширяет состав ПДн, обрабатываемых нами).

## Сессия 15.10.2026

**Платёжная стратегия:** Robokassa официально отказала в подключении магазина для статуса «Самозанятый» (письмо от 15.10.2026), рекомендовав оформить ИП. Техническая реализация (алгоритм подписи SHA256, структура Receipt для НПД, тестовые ссылки оплаты) остаётся верной и описана в `bot.md`, но подключение провайдера заблокировано юридическим статусом, а не техникой. Требуется выбор новой стратегии в следующей сессии.

**Переезд Panel — сервер переустановлен с нуля.** После потери SSH-доступа на первой попытке bootstrap (см. запись 14.10.2026, причина не расследована до конца — вероятная перезапись `authorized_keys` cloud-init при `apt upgrade`) оператор переустановил сервер landvps.ru (`31.77.78.144`) с нуля. Повторный bootstrap выполнен **без** блока SSH/cloud-init харденинга (по явной просьбе оператора), доступ — по паролю.

Результат bootstrap: ufw (22/80/443/2096 Anywhere, 25305 allowlist S1/S2/S_RU/LAN), nginx-заготовка на 80, venv `/opt/netru-bot/venv`, 3x-ui v3.10.2 / Xray v26.10.10 установлены и работают. Память: 961Mi total, available 542Mi (против 159Mi на старом Panel) — подтверждает цель миграции.

Обнаружено: drop-in `/etc/systemd/system/x-ui.service.d/10-xui-sandbox.conf` создаётся **автоматически** официальным install-скриптом x-ui при установке — не требует ручного переноса со старого сервера, как предполагалось в чеклисте миграции (раздел F, п. про systemd-юниты).

**Открыто:** порт панели не удалось сменить с заготовочного `27407` на целевой `25305` — команда `x-ui setting -port 25305` не распознана CLI v3.10.2 (показывает help вместо применения). Панель при этом недоступна извне (порт 27407 не прописан в ufw) — безопасное промежуточное состояние, не блокер, но требует решения в начале следующей сессии через `x-ui setting -h`.

Логин/пароль/webBasePath/API Token панели сгенерированы install-скриптом, сохранены у оператора (не записаны в этот лог).
