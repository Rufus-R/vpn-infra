## Платёжный провайдер: Robokassa (решение 14.10.2026, заменяет ЮKassa)

**Причина смены:** при проверке ЮKassa выяснилось, что для самозанятых (НПД) услуга
«Чеки от ЮKassa» недоступна в принципе (только ИП-неНПД/юрлица) — чек пришлось бы выбивать
вручную через «Мой налог» после каждого платежа. У Робокассы есть отдельное решение
**«Робочеки СМЗ»** — автоматическое формирование чека для самозанятых через интеграцию
с «Мой налог», без ручного шага администратора.

### Доступ
- Идентификатор магазина (`MerchantLogin`): `netru.ru.net`.
- Пароли: `Password#1` (подпись инициации платежа), `Password#2` (подпись `ResultURL`),
  `Password#3` (только для API возвратов, не используется сейчас). Хранятся в
  `secrets/panel-bot.env` (git-crypt) — отдельно тестовая и боевая пара.
- Алгоритм хеша: **SHA256** (выбран явно вместо MD5 во избежание устаревшего алгоритма;
  подтверждён рабочим тестом 14.10.2026 — см. ниже). Установлен в ЛК Robokassa в обоих
  разделах (боевой и тестовый).
- `ResultURL`/`SuccessURL`/`FailURL` — метод отсылки переключён на **POST** (было GET+POST).

### Алгоритм подписи (подтверждено практикой, тестовые платежи MD5 и SHA256 — обе ссылки
открылись без ошибки подписи, 14.10.2026)

**Инициация платежа** (редирект/ссылка на оплату):
```
база = MerchantLogin:OutSum:InvId:<Receipt, urlencode x1>:Password1
SignatureValue = HASH(база)   # SHA256 в проде
```
- `Receipt` участвует в подписи **один раз** URL-кодированным; в самом GET-параметре
  `Receipt` итоговой ссылки — URL-кодирован **дважды** (подтверждено техподдержкой Robokassa
  в письме и рабочим тестом).
- `OutSum` — строка с 2 знаками после запятой (`"200.00"`).

**`ResultURL`** (серверное уведомление об оплате, наш «вебхук»):
```
база = OutSum:InvId:Password2[:Shp_*]
```
- Ответ должен быть строго `OK{InvId}` (например `OK5`), иначе Robokassa повторит попытку.
- IP Robokassa (доп. слой фильтрации в nginx, не основной механизм доверия — основной это
  подпись): `185.59.216.65`, `185.59.217.65`.

### Структура `Receipt` для самозанятого (НПД) — подтверждено письмом техподдержки 14.10.2026

```json
{"items":[{"name":"<название тарифа>","quantity":1,"sum":200.00,"tax":"none"}]}
```
- Поля `sno`, `payment_method`, `payment_object` — **не передавать** (для 54-ФЗ/ИП-неНПД они
  обязательны, но для самозанятого «не несут смысловой нагрузки»; при передаче
  несуществующих/неправильных значений — "чек не будет сформирован из-за ошибки").
- `tax` — строго `"none"`.
- Email для чека/квитанции — Robokassa запрашивает **сама** на своей странице оплаты
  (поле «Email для чека», обязательное у них, не у нас) — подтверждено визуально тестовым
  платежом. **Мы НЕ собираем email клиента в боте** для оплаты — поэтому состав ПДн,
  обрабатываемых нами, не расширяется (можно опционально передать свой `Email` параметром
  для предзаполнения, решено этого не делать).

### Административные предварительные условия (блокируют боевые платежи, НЕ код)

1. **Активация магазина** в ЛК Robokassa — статус на 14.10.2026: заявка подана (получен
   автоответ «в течение одного рабочего дня»), **магазин ещё не активирован**. Тестовый режим
   (`IsTest=1`) работает уже сейчас, независимо от активации.
2. **Партнёрство в «Мой налог»** — для автоформирования чека самозанятого нужно, чтобы в
   приложении «Мой налог» → «Партнёры» появилась запись «Robokassa и НКО «Платежи и
   Расчёты»» и было подтверждено разрешение на взаимодействие с налоговой от имени
   продавца. Статус на 14.10.2026 — **не проверено оператором**, см.
   `next-session-todo.md`.
3. Без обоих условий выше — чек по боевым платежам сформирован не будет, даже если сам
   платёж пройдёт технически успешно.

### Тестовый сценарий — пройден 14.10.2026

Собрана ссылка оплаты вручную (Python-скрипт, без сетевого вызова, только построение URL)
для `MerchantLogin=netru.ru.net`, `OutSum=1.00`, тестовые `Password#1`. Открыта в браузере:
страница Robokassa открылась без ошибки подписи, при раскрытии деталей заказа отображён
верный состав («Тестовый тариф Штиль», 1,00 ₽ × 1) — критерий корректной передачи `Receipt`
от техподдержки выполнен. Проверено для **обоих** алгоритмов (MD5 и SHA256).

### Архитектура интеграции (к реализации, после снятия блокеров выше)

- `ResultURL` обрабатывается **aiohttp.web**-сервером в том же процессе/event loop, что и
  `dp.start_polling()` бота (нужен доступ к объекту `bot` для уведомления пользователя).
  Слушает `127.0.0.1:<порт>`, наружу — через nginx `location` с секретным путём (по аналогии
  с `subPath`/`webBasePath`), не напрямую.
- Переиспользуется логика из уже написанных (но недостижимых с 11.10.2026) хендлеров
  `admin:confirm:`/`admin:reject:` в `tariffs.py` (`add_client → get_client → sub_url`) —
  тот же блок срабатывает по подтверждённому `ResultURL`, а не по нажатию кнопки админом.
- Хранить обе пары паролей (`ROBOKASSA_PASSWORD1_TEST`/`_PROD`, аналогично `_2`) и флаг
  `ROBOKASSA_IS_TEST` — переключение тест→бой без правки кода.
- Идемпотентность: перед обработкой `ResultURL` проверять `Payment.status` (если уже
  `confirmed` — просто вернуть `OK{InvId}`, не создавать клиента повторно) — Robokassa может
  слать уведомление повторно при неответе `OK...`.

### Открытые вопросы (обновлено 14.10.2026)

- Подтвердить активацию магазина и партнёрство в «Мой налог» (блокеры выше).
- Получить боевые `Password#1`/`#2` (отдельно от тестовых).
- Выбрать и согласовать секретный путь для `ResultURL` в nginx + прописать его в ЛК Robokassa.
- Свободный порт для локального вебхук-сервера на Panel — выбран кандидат `8711`,
  не проверен на занятость в этой сессии.
