## Схема сети

```
Интернет
    │
    ▼
[S3: 195.242.118.2]           выход в интернет
 Европа                        (NAT 10.10.0.0/24 -> eth0)
    │
    │  OpenVPN 8443/TCP (tun3 на S1, tun4 на S3)
    │  10.10.0.0/24
    │  S1=10.10.0.1 (сервер, unit openvpn-server@home-s3)
    │  S3=10.10.0.2 (клиент, unit openvpn-client@home-client)
    │
    ▼
[S1: 194.55.236.229]          vpn-admin
 Россия, хаб                   10.9.0.1:8080
    │  OpenVPN tun1
    │  10.9.0.0/24
    │  S1=10.9.0.1 (сервер)
    │
    ├── OPNsense01    10.9.0.5   (opnsense) ──► 192.168.0.0/24 (LAN)
    ├── Mars          10.9.0.10  (family)
    ├── Petr          10.9.0.22  (friend)
    ├── SET01         10.9.0.23  (family)
    ├── Anna          10.9.0.24  (family)
    ├── Serafim       10.9.0.25  (friend)
    ├── Vova          10.9.0.26  (friend)
    └── VovaL         10.9.0.27  (friend)
```

Направление инвертировано 31.10.2026: **сервер теперь на S1**, клиент — на S3. В прямом
направлении (сервер на S3, клиент на S1) DPI рвал соединение примерно через 61 с.

**Почему не `route 0.0.0.0 0.0.0.0`.** В серверном конфиге OpenVPN это системный маршрут:
хост получает `0.0.0.0/1` и `128.0.0.0/1` через туннель, и весь egress уходит туда вместе
с SSH. Нужен `iroute` в файле ccd клиента — он лишь указывает, какому клиенту
инкапсулировать трафик. Именно эта ошибка 31.10.2026 отрезала S1 от сети.

## Логика трафика

1. **Все VPN-клиенты S1** → интернет через **S3** (с 31.10.2026)
   - policy routing: `from 10.9.0.0/24 lookup vpn` (pref 120)
   - таблица vpn: `default dev tun3`
   - NAT на S1: `MASQUERADE 10.9.0.0/24 → tun3`
   - NAT на S3: `MASQUERADE 10.10.0.0/24 → eth0`, `ip_forward=1`
   - маршруты и правила восстанавливает `route-up` сервера `home-s3`
   - порядок `ip rule`: 110 (`to 10.9.0.0/24 → main`), 111 (`from 10.9.0.0/24 to
     192.168.0.0/24 → main`), 120 (`from 10.9.0.0/24 → vpn`).
     Если 110 перекрыть другим правилом, перестаёт работать 111 и клиенты не видят LAN.

2. **Family-клиенты** → дополнительно LAN `192.168.0.0/24` через OPNsense

3. **Friend-клиенты** → только интернет, без LAN

4. **OPNsense** → выход через VPN + NAT на самом OPNsense для LAN-клиентов

4. **OPNsense** → выход через VPN + NAT на самом OPNsense для LAN-клиентов

## DNS

Все VPN-клиенты получают push: `dhcp-option DNS 10.9.0.1`.

Резолвер — **unbound на S1** (установлен 31.10.2026 вместо Pi-hole, который жил на выведенном
S2). Слушает `10.9.0.1:53` и `127.0.0.1:53`, рекурсивный, кэш 24/48 МБ.

- Конфиг: `/etc/unbound/unbound.conf.d/vpn-lan.conf`, копия — `servers/s1/unbound/vpn-lan.conf`
- Доступ: `10.9.0.0/24` разрешён, всё остальное — `refuse`. Открытого резолвера нет.
- `private-address` для `10.9.0.0/24` и `10.10.0.0/24` — DNSSEC не принимает эти подсети
  как публичные адреса.
- Stub-листенер `systemd-resolved` отключён (`/etc/systemd/resolved.conf.d/no-stub.conf`),
  чтобы освободить порт 53. `/run/systemd/resolve/resolv.conf` по-прежнему даёт S1
  upstream (`77.88.8.8`, `8.8.8.8`).

DNS для LAN `192.168.0.0/24` по-прежнему раздаёт OPNsense — unbound туда не втянут.
