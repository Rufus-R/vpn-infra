# Чекпоинт 2026-10-30 — Диагностика туннеля S1↔S3: гипотеза «сдвиг» опровергнута

## Что искали

Продолжение расследования из `checkpoint-2026-10-29-tunnel-s3-probes.md`:
туннель `home-backup` (S1 ↔ S3, TCP 8443, tun2/tun0, 10.10.0.0/24) установлен,
но полезный трафик не проходит. Ведущая гипотеза 29.10 — «сдвиг потока байтов
на константу, НЕ MTU» на основе предупреждения `Bad encapsulated packet length
(16705 = 0x4141)` при любых записях ≥250 B в socat-пробах.

## Главный вывод

**Гипотеза «сдвиг» опровергнута.** Доказательства:

1. `16705 = 0x4141` — это ровно два символа `'A'` из socat-зонда 29.10
   (`0x41` = ASCII `A`), прочитанные как big-endian length-prefix. Варнинг
   OpenVPN корректно «виноват» в кривых данных, которые сам socat и прислал —
   это не индикатор проблемы протокола.

2. Анализ исходников OpenVPN 2.6.19 (`socket.c`):
   - length-prefix — `uint16_t` big-endian (`packet_size_type`), читается из
     `sb->buf` **без смещений**: `stream_buf_added()` переносит «хвост» через
     `buf_copy_n(dest, sb->buf, sb->len)` после `buf_advance(&sb->buf, sb->len)`;
   - «сдвиг на константу» не может пройти через TLS-аутентификацию контрольного
     канала (tls-crypt + TLS 1.3) — хендшейк бы не завершился;
   - «сдвиг», генерирующий ровно `0x4141`, — совпадение 1 : 65536 на каждый пакет,
     вероятность нулевая. Два байта probe-данных объясняют значение точно.

3. Симптом другой: туннель **устанавливается** (TLS-хендшейк, PUSH_REPLY,
   Data Channel AES-256-GCM), затем первый же пакет данных не подтверждается
   и обе стороны сбрасывают сессию по `--ping-restart` (~61–62 с цикл). Статус:
   постоянный флап, полезная связность 10.10.0.0/24 отсутствует.

## Матрица тестов (30.10, всё с S1 по цепочке SSH → S3/S_RU)

| Тест | Результат |
|---|---|
| Plain TCP S3→S1 (9700, 7×110 B @ 10 с) | 770/770 B — OK |
| Plain TCP S1→S3 (9911, инициатор S1) | conn timeout — НЕ прошла |
| Plain TCP bidir 9900 (srv S1) | 9/9 обе стороны — OK |
| Plain TCP 8444 (rnd payload) | 5/5 — OK |
| **Plain TCP 8443 (rnd payload)** | **5/5 — OK** |
| Plain UDP S1→S3 (9444, 20×110 B) | 0/20 на S3 при ufw ALLOW |
| ICMP в обе стороны, 1400-B пакеты | 0% потерь |
| OpenVPN TCP 8443 (prod home-backup) | handshake OK → data channel не живёт (flap ~61 с) |
| OpenVPN TCP 9443 (тестовый сервер на S3) | handshake OK → тот же флап |
| OpenVPN UDP 9444 (тестовый сервер на S3) | handshake OK → ping 100% loss |

Вывод: port/transport-независимо, но специфично для **формата OpenVPN**; обычный
TCP/UDP на тех же портах проходит. OpenVPN-инициированное соединение S1→S3 даже
не устанавливается на транспортном уровне (plain TCP connect timeout), тогда как
S3→S1 TCP работает. TCP-пакеты OpenVPN обе стороны видят в tcpdump (110-B
сегменты), но ACK не возвращается — дроп после рукопожатия на пути/в ядре.

Профиль согласуется с **активной блокировкой/манипуляцией DPI** (TSPU и т.п.):
рукопожатие пропускается, паттерн data-channel-пакетов режется; plain TCP на тех
же портах проходит, UDP в обе стороны почти не доходит. Точная механика не
доказана — нужны контрольные точки (VPS в нейтральной сети, IPv6, обфускация).

## Прочие находки

- На S3 у 8443 висит зомби-сокет `FIN-WAIT-1` (ino:0, нет владельца) с вечными
  ретрансляциями — следствие, не причина; лечится перезапуском службы/ waiting.
- `TcpInCsumErrors` на S1 — 8268 ( historically, проверки checksum через tcpdump
  не показали real-проблем на 8443; шум вероятно от другого трафика/этого же).
- `sru-transport` (S_RU ↔ S3, 1195) поднят, но **клиента на S_RU нет**
  (openvpn не установлен) — правило ufw ожидает 31.77.169.67, а соединений нет.
- Xray на S1 нет; socks5 tg-proxy (38417) на S3 работает (из предыдущей сессии).

## Рекомендации (порядок)

1. **Не реанимировать TCP-OpenVPN как основную связку S1↔S3.** Профиль — DPI.
   Варианты обхода:
   a) Xray/Reality-обёртка: S1 ставит xray-клиент, S3 уже имеет xray (relay);
      туннель OpenVPN инкапсулировать в VLESS/Reality TCP 443 к S3 (пример:
      `kvas`/`tun2socks` или обычный `xray` inbound+outbound с sniffing);
   b) Перевести S1↔S3 на **WireGuard** (UDP) — но plain UDP S1→S3 в тесте тоже
      почти не прошёл (0/20 при ALLOW); требуются доп. проверки с разных VPS
      прежде чем ставить на UDP;
   c) ICMP-туннель (Hans/icmptx) — экзотика, не рекомендуется.
2. **Быстрое восстановление связности для панели/бота**: не блокирует бизнес —
   bot ходит через socks5 tg-proxy на S3 (работает), коммерческий канал
   клиент→S_RU→S3:10001 работает. S1↔S3 нужен только как резерв home-канала.
3. Проверить с нейтрального VPS: OpenVPN S1→S3 и plain-TCP в обе стороны —
   определить, режется ли конкретно S1↔S3-путь (для тикета провайдеру S1/S3).
4. Для S_RU↔S3: сначала установить openvpn на S_RU (или решить, что transport
   больше не нужен, и почистить ufw/конфиг на S3 + задокументировать).

## Изменения в инфраструктуре

Тестовые конфиги/правила UFW/файлы на S3 и S1 удалены после диагностики.
Существующие сервисы не тронуты: `openvpn-server@home-backup` (S3) и
`openvpn@s3-backup` (S1) работают в штатном (хотя и бесполезном из-за DPI)
режиме, `xray-relay` (10001) активен, статус `sru-transport` — active.
