# Чекпоинт 31.10.2026 — S1 потерян при переводе домашнего OpenVPN на S3 (АВАРИЯ, доступ только через консоль провайдера)

ВНИМАНИЕ: S1 (`194.55.236.229`, `maximum.ru.net`) **недоступен по сети** с ~12:52 МСК.
Все внешние порты (22, 80, 443, 1194, 8080, 8443) не отвечают, ICMP 0%. Причина —
изменение, внесённое агентом в серверный конфиг OpenVPN. Нужно восстановление через
KVM-консоль провайдера S1 (по кнопке оператора). Ниже — что именно сделать.

## Что было сделано (факты, по времени МСК)

Задача: перевести домашний эгресс на S3, т.к. S2 недоступен (подтверждено: ping 100%
loss, TCP 22 timeout, `openvpn-client@s2-client` флапает `TLS key negotiation failed`).

Подготовлено и работало:

- На S3 (PKI `/etc/openvpn-easyrsa`) выписаны `s1srv` (сервер) и `home-client` (клиент).
- На S1: каталог `/etc/openvpn/server-home-s3/` (`ca.crt`, `s1srv.crt`, `s1srv.key`, `ta.key`),
  конфиг `/etc/openvpn/server/home-s3.conf` — 8443/TCP, `dev tun3`, `topology subnet`,
  `server 10.10.0.0 255.255.255.0`, AES-256-GCM, tun-mtu 1300, keepalive 10 60.
- На S3: `/etc/openvpn/client/home-client.conf` (inline ca/cert/key/tls-auth, `dev tun4`),
  unit `openvpn-client@home-client` — **туннель поднялся, стабилен >3 мин, MTU 1400 OK**.
- На S1: таблица `vpn` переключена на `default dev tun3`; NAT
  `-A POSTROUTING -s 10.9.0.0/24 -o tun3 -j MASQUERADE` (вместо `-o tun0`).

## Причина аварии

Чтобы сервер S1 инкапсулировал в туннель пакеты с адресами ВНЕ пула `10.10.0.0/24`
(выход в интернет через S3), в `/etc/openvpn/server/home-s3.conf` были добавлены строки:

```
client-config-dir /etc/openvpn/ccd-home-s3
route 0.0.0.0 0.0.0.0
```

**Ошибка:** `route 0.0.0.0 0.0.0.0` в серверном конфиге OpenVPN — это не iroute, а
СИСТЕМНЫЙ маршрут. OpenVPN ставит на хосте `0.0.0.0/1` и `128.0.0.0/1` через `tun3`, то есть
весь egress S1 (включая SSH-ответы и всё исходящее) уходит в туннель. Правильная конструкция —
`iroute 0.0.0.0 0.0.0.0` **только** в файле ccd клиента, без `route` в server.conf.
После рестарта юнита S1 потерял внешний доступ.

## Вторая ошибка в диагностике (важно, чтобы не повторять)

В подсети `10.10.0.0/24` на S3 оказались ДВА интерфейса: старый сервер
`openvpn-server@home-backup` держал `tun0 = 10.10.0.1/24`, новый клиент — `tun4 = 10.10.0.2/24`.
Поэтому:

1. Проверка «ping 10.10.0.2 ↔ 10.10.0.1 — 0% потерь» была **ложноположительной**: пакеты не
   покидали S3.
2. «Вход в S1 по 10.10.0.1» через ProxyCommand на самом деле заходил на S3 (hostname вернул
   `s3s3.s2`), что дополнительно скрыло аварию.

После этого `openvpn-server@home-backup` на S3 остановлен и disabled (что и так планировалось),
но S1 к тому моменту уже был недоступен: туннель не переустанавливается
(`TCP: connect to 194.55.236.229:8443 failed: Connection timed out`).

## ВОССТАНОВЛЕНО (31.10.2026, ~15:40 МСК)

Оператор в KVM-консоли провайдера выполнил `systemctl stop openvpn-server@home-s3` —
OpenVPN при штатной остановке сам снял маршруты `0.0.0.0/1` и `128.0.0.0/1`, внешний доступ
вернулся (консольный ввод без вставки, поэтому давались только простые команды).

Далее по SSH с OpenHands:

1. `systemctl disable openvpn-server@home-s3` — страховка от повторения (позже, после
   проверки, снова `enable`, т.к. сервер должен подниматься при загрузке).
2. Из `home-s3.conf` удалена строка `route 0.0.0.0 0.0.0.0` (`iroute` остался только в ccd).
3. Обнаружен **конфликт подсетей**: старый клиент `openvpn@s3-backup` держал
   `tun2 = 10.10.0.2/24` одновременно с новым сервером `tun3 = 10.10.0.1/24`. Клиент
   остановлен и **masked** (иначе поднимался при ребуте).
4. Сервер поднят: `tun3 = 10.10.0.1/24`, 8443 слушает, "маршрутов-угона" нет.
5. Клиент на S3 перезапущен (ушёл в backoff 300 с). Туннель: ping `10.10.0.1`
   **47 мс** (реальный путь через интернет, не локальный), 70 с без рестартов,
   пакеты 1200 B проходят.
6. Persistence:
   - `/etc/openvpn/server/route-up-home-s3.sh` + `script-security 2` + `route-up` в
     `home-s3.conf` — ставит `ip rule` 110/111/120 и `default dev tun3` в таблице `vpn`.
   - **Грабли:** без `script-security 2` OpenVPN молча не запускает `route-up`
     (`WARNING: Failed running command (--route-up): disallowed by script-security setting`),
     таблица `vpn` остаётся пустой.
   - NAT `10.9.0.0/24 -o tun3` в `/etc/iptables/rules.v4` + `netfilter-persistent save`.
   - Из `/etc/openvpn/client/route-up.sh` удалён мёртвый `default via 10.8.0.1 dev tun0`
     (он возвращал маршрут на S2 при рестарте `s2-client`).
7. Восстановлен порядок `ip rule` по документации: `pref 110` =
   `to 10.9.0.0/24 → main` (было ошибочно `from 10.9.0.0/24 → vpn`, из-за чего не работал
   `pref 111` и клиенты не видели LAN `192.168.0.0/24`).
8. DNS: Pi-hole на S2 (`10.8.0.1`) мёртв → `push "dhcp-option DNS 1.1.1.1"` в
   `server.conf` (проверено: DoH и UDP/53 до 1.1.1.1 проходят через новый путь).

## Правило «откат без подтверждения» (по итогам аварии)

Оператор потребовал механизм, чтобы авария не повторилась. Требование
«не добавлять OpenVPN в автозагрузку» отклонено: без автозапуска S1 не вернётся
после ребута (проверено в этой же сессии — ребут 16:44 поднял всё сам).

Принято: **автозапуск остаётся, а рядом ставится сторож с таймером.**

- `servers/s1/scripts/openvpn-guard.sh` — `check | confirm | revoke | status`.
- `servers/s1/systemd/openvpn-guard.service` + `.timer` — проверка каждые 60 с,
  первый запуск через 30 с после загрузки.
- Пока оператор не выполнил `confirm`, сторож снимает маршруты-угона
  `0.0.0.0/1` и `128.0.0.0/1` из главной таблицы; три срабатывания подряд — останавливает
  `openvpn-server@home-s3`.
- Лог `/var/log/openvpn-guard.log`, состояние в `/etc/openvpn-guard/`.

Логика проверена в песочнице с заглушкой `ip` (4 сценария): откат при неподтверждённом
конфиге, бездействие при подтверждённом, бездействие при чистой таблице, эскалация до
остановки юнита после 3 попыток. На живом сервере **ещё не развёрнуто** — ждёт одобрения
оператора и отдельной проверки.

Правило внесено в регламент: `docs/agent-workflow.md` §12.

## Восстановление через консоль провайдера S1 (по кнопке оператора)

Рекомендуется просто **перезагрузить S1** из консоли: `openvpn-server@home-s3` включён
(`enabled`), на старте он снова поставит `0.0.0.0/1` и `128.0.0.0/1`, т.е. после ребута
сеть останется сломанной. Поэтому порядок — сначала в консоли (до ребута или recovery-режим):

1. **Немедленно, если консоль есть на живой системе:** удалить строку `route 0.0.0.0 0.0.0.0`
   из `/etc/openvpn/server/home-s3.conf`, оставив `client-config-dir`, и выполнить:
   ```bash
   systemctl stop openvpn-server@home-s3
   ip route del 0.0.0.0/1 dev tun3 2>/dev/null
   ip route del 128.0.0.0/1 dev tun3 2>/dev/null
   ```
   После этого внешний SSH должен вернуться (проверить снаружи `22/tcp`).
2. **Если система недоступна и нужен ребут:** в консоли/через recovery:
   ```bash
   mount -o remount,rw /
   sed -i '/^route 0.0.0.0 0.0.0.0$/d' /etc/openvpn/server/home-s3.conf
   systemctl disable openvpn-server@home-s3
   reboot
   ```
   Ключевое — `disable` до ребута, иначе маршрут вернётся.
3. После возврата SSH — сообщить агенту, продолжить настройку по исправленному плану
   (см. ниже).

Правильный вариант серверного конфига (без системного маршрута):

```ini
port 8443
proto tcp
dev tun3
topology subnet
server 10.10.0.0 255.255.255.0
ca /etc/openvpn/server-home-s3/ca.crt
cert /etc/openvpn/server-home-s3/s1srv.crt
key /etc/openvpn/server-home-s3/s1srv.key
dh none
tls-auth /etc/openvpn/server-home-s3/ta.key 0
data-ciphers AES-256-GCM
tun-mtu 1300
keepalive 10 60
user nobody
group nogroup
persist-key
persist-tun
disable-dco
client-config-dir /etc/openvpn/ccd-home-s3
verb 3
```

`/etc/openvpn/ccd-home-s3/home-client`:

```
iroute 0.0.0.0 0.0.0.0
```

`iroute` только сообщает серверу, какому клиенту инкапсулировать такие пакеты; системных
маршрутов он не создаёт.

## Что дальше после восстановления доступа

1. Исправить конфиг по образцу выше, рестарт `openvpn-server@home-s3`.
2. Проверить туннель **честно**: `ping 10.10.0.1` с S3 при **отсутствии** второго
   интерфейса в `10.10.0.0/24` (на S3 осталось только `tun4`).
3. Проверить egress: с S1 `curl --interface 10.9.0.1 http://ip-api.com/line/?fields=query`
   должен вернуть IP S3 (`195.242.118.2`).
4. Проверить, что `10.9.0.0/24` и LAN-правила (`pref 110/111`) не задеты.
5. Только после этого — отключать старые юниты (`openvpn-client@s2-client`,
   `openvpn@s3-backup`).
6. DNS-замена Pi-hole (S2 недоступен): в `home-s3.conf` добавить
   `push "dhcp-option DNS 1.1.1.1"` / `8.8.8.8` — решение оператора.
7. Персистентность: NAT-правило `10.9.0.0/24 -o tun3` внести в `/etc/iptables/rules.v4`;
   таблицу `vpn` (default dev tun3) восстановить при старте (route-up-скрипт или
   systemd-unit), сейчас она живёт только в рантайме.
