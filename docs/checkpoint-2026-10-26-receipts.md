## Факты

- Токен доступа живёт около часа (обновление в 09:59 UTC, `tokenExpireIn` 10:59:21 UTC). Обновление ленивое: при первом запросе после истечения или за минуту до него.
- `refreshTokenExpiresIn` в `token.json` — `null`, срок жизни refresh-токена неизвестен. Ежедневная проверка в 09:00 МСК обновляет токен каждый раз и держит его живым; если refresh-токен перестанет приниматься, алерт админам сообщит о состоянии `rejected`.
- Исходы `issue_receipt`: `retry` — только `ConnectionException` и сбои получения ИНН до создания чека; `unknown` — таймаут и прочие сетевые ошибки, 5xx, неразобранный ответ, ответ без `approvedReceiptUuid`; `failed` — 400, 401, 403, 404, 406, 422, 429 и ошибки данных. `POST /income` не идемпотентен, любые сомнения — `unknown`.
- Тело запроса: `paymentType: ACCOUNT`, название позиции `Штиль: <service_name>`, сумма из копеек строкой с двумя знаками (`250.00`), время операции — aware-UTC (время платежа в БД наивное UTC), будущее время обрезается до «сейчас» (ФНС отвечает 422 на будущую дату).
- Ссылка на чек: `https://lknpd.nalog.ru/api/v1/receipt/<ИНН>/<UUID>/print`; ИНН берётся из `profile` в `token.json`, при отсутствии — из `user().get()`, кэшируется в процессе.
- Проверка токена: первая через 30 секунд после старта бота, затем ежедневно в 09:00 МСК; при `unavailable` до 3 попыток с паузой 10 минут; состояние (`ok` / `rejected` / `unavailable`) — в памяти процесса, алерт админам при смене состояния (после рестарта при нерабочем токене возможен один повторный алерт), сообщение о восстановлении.
- Платёж #4 (`Бриз · Общая палуба`, 250 ₽) — тестовый платёж ЮKassa самого оператора; чек #1 на него не выпускается. Платёж #5 (`Фарватер · Общая палуба`, 2250 ₽, создан 26.10.2026 14:21) — реальный покупатель в тестовом магазине, без реальных денег; чек #2 на него тоже не выпускается. ## Решения оператора (26.10.2026)

1. Время операции в чеке — подтверждение платежа в БД (`receipts.created_at`).
2. Название позиции — с префиксом «Штиль: » (как описание платежа в ЮKassa).
3. Состояние проверки токена — в памяти процесса, запуск в 09:00 МСК.
4. Выпуск чеков первое время — только вручную админом, с экраном подтверждения «создать настоящий чек?» (кнопки «Да, выпустить» / «Отмена»).
5. Для `unknown` кнопки «Чек есть в приложении» (статус `sent` без ссылки, пользователю ссылка не уходит) и «Вернуть в очередь»; для `failed` — «Вернуть в очередь»; ручной ввод ссылки не нужен (при необходимости добавим).
6. Напоминание админам о чеках старше суток: код пишется, но в `main.py` подключается только после запуска боевого магазина ЮKassa.

## Дизайн патча №3 (реализован 26.10.2026, см. «Выполнено»)

- Модуль `app/receipts.py`: атомарный переход `pending_review → sending` (`UPDATE ... WHERE status = 'pending_review'`, проверка числа строк, `commit` до вызова API); вызов `nalog.issue_receipt(service_name, amount, receipts.created_at)`; запись результата: `sent` (`receipt_uuid`, `receipt_url`, `sent_at`, ссылка пользователю сообщением в бот, отчёт админам), `failed` (`error`), `unknown` (`error`, уведомление админам), `retry` (возврат в `pending_review` с записью в `error`). Реализовано дополнительно к дизайну: единый с проверкой токена семафор запросов к ФНС (выпуск и `check_token` не идут параллельно), `requeue` только из `failed`/`unknown`, `confirm_manual` только из `unknown` (помечает «подтверждено админом вручную: чек есть в приложении»).
- Восстановление при старте бота: `sending → unknown` (`mark_interrupted`), как у рассылки и напоминаний.
- Админ-меню: экран «Чеки к выдаче» получает кнопки по каждому чеку; экран подтверждения перед выпуском; для `unknown` и `failed` — кнопки решений (п. 5 выше); защита от двух админов обеспечивается атомарным переходом. Реализовано дополнительно: защита от двойного нажатия кнопки выпуска, карточка `sent` показывает ссылку, для `pending_review` при выключенном флаге — подсказка про `NALOG_ISSUE_ENABLED`.
- Миграций нет: статус — свободная строка (до 16 символов), поля `receipt_uuid`, `receipt_url`, `error`, `sent_at` уже есть — подтверждено тестом на копии (версия схемы осталась `0007`).
- Флаг выпуска: `NALOG_ISSUE_ENABLED` читается из окружения при старте; `issuing_enabled()` требует и флага, и существующего каталога состояния (`NALOG_STATE_DIR`, на Panel это `/root/.secrets/nalog`). По умолчанию выключен.
