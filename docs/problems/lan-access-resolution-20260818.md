## РЕШЕНО (18.08.2026)

### Итоговая первопричина

Проблема "family → LAN не работает" и отдельно всплывшая в этой же
сессии проблема "иногда пропадает пинг из LAN к 10.9.0.1" оказались
проявлениями одной и той же первопричины: конфликт Virtual Address
между статически назначенным `OPNsense01` (`10.9.0.5` через
`ifconfig-push`) и клиентами, получавшими адреса динамически из общего
пула сервера, который не исключал занятые статикой адреса.

Ранее задокументированное наблюдение "маршрут `192.168.0.0/24 via
10.9.0.2 dev tun1` вместо `via 10.9.0.5`" не являлось самостоятельной
проблемой маршрутизации ядра — в режиме `topology subnet` с
`client-to-client` внутренняя доставка iroute-трафика идёт через
логику самого процесса OpenVPN, минуя таблицу маршрутизации ядра.
Этот пункт закрывается как false positive, отдельного исправления не
требует.

Реальная первопричина обеих проблем подробно описана в
[known-issues.md](known-issues.md), раздел "Конфликт Virtual Address
между статикой и динамическим пулом".

### Диагностический путь (кратко)

1. Подтверждено: ICMP от OPNsense к `10.9.0.1` реально покидает
   интерфейс `ovpnc1` на OPNsense (`tcpdump` на OPNsense).
2. Подтверждено: зашифрованный UDP/1194-трафик реально доходит до
   `ens3` на S1 (`tcpdump` на S1).
3. Подтверждено: расшифрованные пакеты не появляются на `tun1`
   (широкий `tcpdump -ni tun1` без фильтра, `0 packets captured`).
4. Обнаружено прямое совпадение Virtual Address `10.9.0.5` у двух
   разных Client ID в `openvpn-status-tun1.log` (`OPNsense01` и
   `VovaL`) — прямое, не косвенное доказательство конфликта.

### Решение

Всем валидным клиентам назначены статические `ifconfig-push`-адреса
через CCD (диапазон `10.9.0.22–10.9.0.28` для ранее динамических
клиентов), `server.conf` оставлен без изменений. Подробности и
рассмотренные альтернативы — в `known-issues.md`.

### Подтверждение исправления

- `ping -c 10 10.9.0.1` с OPNsense: 0% потерь (после исправления).
- Клиент `Petr`, переподключившийся спустя несколько часов после
  внесения изменений, корректно получил назначенный статический адрес
  `10.9.0.22` — подтверждено по `openvpn-status-tun1.log`.
