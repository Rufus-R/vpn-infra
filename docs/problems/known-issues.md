```bash
  >> /etc/openvpn/server/server.conf
systemctl restart openvpn-server@server
```

### 5. S1: неизвестное правило tcp/10443 (РЕШЕНО 26.09.2026 — демонтаж MTProxy)
В INPUT есть `ACCEPT tcp/10443` — неизвестное назначение.
Вероятно тестовый порт MTG, забыт.

**Проверить и удалить**:
```bash
iptables -vnL INPUT --line-numbers | grep 10443
# Найти номер строки и удалить
iptables -D INPUT <номер>
netfilter-persistent save
```

### 6. S1: открытые порты 8443/9443 без работающего сервиса (РЕШЕНО 26.09.2026 — демонтаж MTProxy)
MTG на 8443/9443 не запущен, но iptables разрешает входящие.

**Исправить когда решится судьба MTG**:
```bash
# Убрать 8443,9443 из правила, оставить только 443
iptables -D INPUT -p tcp -m multiport --dports 443,8443,9443 -j ACCEPT
iptables -A INPUT -p tcp --dport 443 -j ACCEPT
netfilter-persistent save
```

### 7. S1: маршрут 192.168.0.0/24 via 10.9.0.2 (ЗАКРЫТО как false positive, 18.08.2026)
Объяснено в [lan-access-resolution-20260818.md](lan-access-resolution-20260818.md): в режиме `topology subnet` с `client-to-client` iroute-трафик между VPN-клиентами обрабатывается логикой самого процесса OpenVPN, минуя таблицу маршрутизации ядра — этот маршрут не влияет на реальную доставку пакетов. Отдельного исправления не требует.

## [РЕШЕНО 27.09.2026] Критическая уязвимость: открытый DNS-резолвер и админ-панель Pi-hole на S2

### Симптом / обнаружение

Обнаружено случайно при диагностике доступности 3x-ui нод коммерческого
проекта (`curl` к порту 25307 на S2 завис вместо быстрого ответа/ошибки).
При проверке iptables на S2 выявлено, что правила для портов 80/tcp,
53/tcp, 53/udp были в неверном порядке: ACCEPT для `0.0.0.0/0` стоял
**выше** DROP-правил, из-за чего DROP никогда не срабатывал
(first-match-wins в iptables).

### Реальный эффект (до исправления)

- **Pi-hole DNS (53/tcp+udp)** был полностью открытым публичным
  DNS-резолвером — доступен из любой точки интернета. Риск: DNS
  amplification атаки с использованием сервера как усилителя, паразитная
  нагрузка, потенциальный abuse-репорт от хостера.
- **Pi-hole web admin (80/tcp)** был доступен всему интернету без
  ограничений — риск брутфорса пароля админки и эксплуатации возможных
  уязвимостей веб-интерфейса.
- **OpenVPN (1194/udp)** был открыт всем источникам без ограничения —
  для этого порта не было DROP-правила вообще (не просто неверный
  порядок, а полное отсутствие catchall).

Документация (`architecture/overview.md`) при этом ошибочно утверждала,
что Pi-hole "слушает на `10.8.0.1:53` (только через tun0)" — в
реальности сервис (`pihole-FTL`) слушает на `0.0.0.0` для всех своих
портов (53, 80, 443, 123), биндинг никогда не был ограничен интерфейсом.
Вся изоляция обеспечивалась (и обеспечивается сейчас) исключительно
правилами iptables.

Попутно подтверждено: порты 443/tcp и 123/udp (тоже Pi-hole) были
задропаны корректно уже до этого инцидента — старая запись №4 в этом
файле, утверждавшая обратное, была ошибочной.

### Причина

Вероятное накопление дублей и нарушение порядка — правки iptables через
`iptables -I` (вставка в начало цепочки) в разное время, в т.ч. при
недавней настройке 3x-ui relay для коммерческого проекта, без ревизии
итогового порядка правил относительно старых DROP-catchall.

### Исправление

На S2 правила 6,7,8 (ACCEPT для 80/tcp, 53/udp, 53/tcp) заменены через
`iptables -R` с добавлением источника `10.8.0.0/24` (только тоннель
S1↔S2). Для 1194/udp добавлен недостающий DROP-catchall в конец
цепочки, затем правило ACCEPT сужено до источника `194.55.236.229`
(единственный легитимный клиент — S1).

Проверено после применения:
- `dig @10.8.0.1 google.com` (через тоннель) — работает
- `dig @77.105.161.151 google.com` (напрямую, внешний IP) — timeout,
  подтверждена недоступность извне
- `curl http://10.8.0.1/admin/` (через тоннель) — 302, панель доступна
- `ping 10.8.0.1` — туннель не пострадал

Правила сохранены персистентно: `netfilter-persistent save`.

Актуальная итоговая таблица правил и техдолг (дубль MASQUERADE,
пустой ip6tables): [../networking/iptables-s2.md](../networking/iptables-s2.md)

### Оставшийся риск

`ip6tables` на S2 полностью пуст (policy ACCEPT, 0 правил) — если у
сервера есть маршрутизируемый IPv6, все вышеописанные порты могут быть
доступны через IPv6 в обход всех сегодняшних исправлений. Требует
отдельной проверки в следующей сессии.



## [РЕШЕНО 18.08.2026] Конфликт Virtual Address между статикой и динамическим пулом

### Симптом

Периодическая, не всегда воспроизводимая потеря связи между OPNsense01
и сервером S1 (`ping 10.9.0.1` со стороны OPNsense — от 0% до 100% потерь
в зависимости от момента), при этом:
- мобильные VPN-клиенты продолжали работать нормально;
- LAN-доступ через iroute иногда продолжал работать даже при потере
  прямого ICMP к `10.9.0.1` (см. следующий пункт про диагностику).

### Первопричина

Клиент `OPNsense01` получает статический адрес `10.9.0.5` через
`ifconfig-push` в CCD. До 18.08.2026 в `server.conf` не было отдельного
`ifconfig-pool` — статические адреса **не были исключены** из общего
динамического пула `server 10.9.0.0 255.255.255.0`.

Когда новый клиент (`VovaL`, без CCD) подключался и получал из общего
пула тот же адрес `10.9.0.5`, что и статически закреплённый за
`OPNsense01`, внутренняя таблица маршрутизации OpenVPN для этого адреса
перезаписывалась в пользу новой сессии. Пакеты, адресованные `10.9.0.5`
(включая ICMP-ответы от OPNsense), уходили не туда до тех пор, пока
конфликтующая сессия не завершалась.

Подтверждено прямым наблюдением: `openvpn-status-tun1.log` в момент
сбоя показывал одновременно `CLIENT_LIST,OPNsense01,...,10.9.0.5,...` и
`CLIENT_LIST,VovaL,...,10.9.0.5,...` — совпадение Virtual Address у двух
разных Client ID.

### Диагностика: почему LAN-доступ иногда работал, а прямой ping — нет

`client-to-client` трафик между VPN-клиентами (например, LAN за
OPNsense01 ↔ мобильный клиент) обрабатывается полностью внутри процесса
OpenVPN и не проходит через интерфейс `tun1`/ядро — таким образом он не
зависел от конфликта на уровне ядра/iptables. Прямой ICMP к `10.9.0.1`
(адресу самого сервера) обязан пройти через `tun1` и INPUT-цепочку
ядра — именно этот путь ломался конфликтом.

### Рассмотренные варианты решения

**Вариант A (опробован первым, отклонён)**: добавить в `server.conf`
явный `ifconfig-pool 10.9.0.20 10.9.0.254`, исключив статические адреса
из пула. Директива `server` в режиме `topology subnet` неявно задаёт
`ifconfig-pool` сама — потребовалось раскрыть её в явную форму
(`mode server` + `tls-server` + `ifconfig` + `ifconfig-pool`). Это
раскрытие имело два непредвиденных побочных эффекта, обнаруженных
только на живых клиентах:
1. Пропала автоматическая настройка `route-gateway` для серверных
   `route`-директив (устранено добавлением `route-gateway 10.9.0.1`).
2. Пропал автоматический push `topology subnet` клиентам, что вызывало
   ошибку `tun_prop_error: ifconfig addresses are not in the same /30
   subnet (topology net30)` у части клиентов (устранено добавлением
   `push "topology subnet"`).

После исправления обеих проблем конфигурация проходила синтаксическую
проверку и тестовый запуск, но при применении на проде вызвала новую,
не до конца диагностированную регрессию: клиент `SET01` не мог
установить сессию (`ovpnagent: request error`, повторяющиеся
`Inactivity timeout`/`ping-restart`), клиент `Mars` устанавливал сессию,
но реальный трафик (интернет, LAN) не проходил при полностью рабочем
ICMP. Точная причина этой регрессии не установлена — решено не тратить
дальнейшее время на диагностику работающей продакшн-системы и **откатить**
изменение.

**Вариант B (применён)**: не менять `server.conf` вообще. Вместо этого
назначить статический `ifconfig-push` **всем** валидным клиентам
(включая ранее динамических: Petr, SET01, Anna, Serafim, Vova, VovaL) в
диапазоне `10.9.0.22–10.9.0.28`, оставив общий пул `server.conf`
нетронутым. Поскольку каждый клиент теперь имеет фиксированный адрес,
динамический пул фактически не используется, и коллизия структурно
исключена независимо от порядка/момента подключения клиентов.

Преимущество варианта B, подтверждённое на практике: изменение CCD не
требует перезапуска `openvpn-server@server` и не затрагивает уже
установленные сессии других клиентов — в отличие от правки
`server.conf`, которая требует полного рестарта сервиса и разом
затрагивает всех подключённых клиентов.

### Применённое решение

`server.conf` оставлен в исходном виде (директива `server 10.9.0.0
255.255.255.0`, без явного `ifconfig-pool`). CCD-файлы для всех клиентов
без ранее существовавшей статики дополнены `ifconfig-push`:

| Клиент | Новый статический адрес |
|--------|--------------------------|
| Petr | `10.9.0.22` |
| SET01 | `10.9.0.23` |
| Anna | `10.9.0.24` |
| Serafim | `10.9.0.25` |
| Vova | `10.9.0.26` |
| VovaL | `10.9.0.27` |

`10.9.0.28` оставлен свободным резервом.

Подтверждено фактически (не только теоретически): клиент `Petr`
переподключился в 21:29 (спустя часы после записи CCD) и получил
корректный `10.9.0.22` — механизм работает.

### Оставшийся риск на будущее

`vpn-admin/app.py` создаёт CCD автоматически только для групп `family`
и `opnsense`; группа `friend` CCD не получает и при создании через
веб-панель попадёт в общий динамический пул. Любой новый клиент,
созданный через vpn-admin как `friend`, должен получить `ifconfig-push`
**вручную** после создания, в диапазоне выше `10.9.0.28` (следующий
свободный — `10.9.0.29`), пока это поведение `app.py` не будет
исправлено отдельно.

Если в будущем всё же потребуется вернуться к явному `ifconfig-pool` в
`server.conf` — нижнюю границу пула необходимо задать не ниже
`10.9.0.30`, чтобы не пересекаться с уже зарезервированным статическим
диапазоном `10.9.0.2–10.9.0.28`. При этом стоит учитывать, что
вариант A уже показал скрытые регрессии (см. выше) — потребуется более
осторожное, пошаговое применение с проверкой на живых клиентах, а не
разовое изменение сразу нескольких директив.


## [РЕШЕНО 26.09.2026] MTProxy демонтирован полностью

### Причина

MTG (порт 443) не работал стабильно во время реальных блокировок
(timeout при подключении к fronting-доменам, см. архивный
`services/archive/mtg-deprecated-20260926.md`). Признан
нежизнеспособным, принято решение о полном демонтаже, а не о доработке.

### Что сделано

- Остановлены и отключены `mtg@443`, `mtg@8443`, `mtg@9443`
- Удалены `/etc/mtg`, `/usr/local/bin/mtg`, `/etc/systemd/system/mtg@.service`
- Удалён пользователь `mtproxy` (UID 999)
- iptables: удалены правила INPUT для портов `10443` и `443,8443,9443`,
  mangle-разметка `uid 999`, NAT `MASQUERADE` для `uid 999`
- Policy routing: удалено правило `ip rule fwmark 100 table 100`,
  таблица `100` очищена
- `route-up.sh` очищен от блока создания правила/маршрута для MTProxy

Закрывает пункты 5 и 6 этого файла.

### Побочная находка: баг в route-up.sh (исправлен попутно)

При редактировании `/etc/openvpn/client/route-up.sh` обнаружено, что
строки
```
ip rule add from 10.9.0.0/24 table vpn pref 120 2>/dev/null || true
ip route add default via 10.8.0.1 dev tun0 table vpn 2>/dev/null || true
```
были слиты в файле в одну строку без разделителя (`...|| trueip route
add...`), из-за чего вторая команда фактически являлась частью
аргумента к `true` и никогда не выполнялась. Таблица `vpn` в системе до
этого момента существовала только как live-объект ядра, оставшийся с
более раннего запуска — не создавалась заново самим скриптом при
каждом up-событии туннеля `openvpn-client@s2-client`.

Исправлено при той же правке: файл перезаписан с явным разделением
строк, подтверждено через `cat -A` (оба `\n` на месте).

**Риск был**: при полной перезагрузке сервера или пересоздании
интерфейса `tun0` маршрут `default via 10.8.0.1 dev tun0` в таблице
`vpn` не создался бы автоматически — весь трафик клиентов (10.9.0.0/24)
потерял бы выход в интернет через S2 до ручного вмешательства.
