Связка «мастер ↔ нода S3» рабочая: подписка с `2096` стабильно отдаёт 2 ссылки

## 2. Ложная тревога: `subLinks` = 0 и «subId сброшен»

Симптом: `GET /clients/subLinks/<subId>` возвращал `success=true, n=0`
сразу для всех клиентов.

Причина 1 — **устаревший источник subId**. В `inbounds.settings.clients`
у клиента лежал `subId=pktkh9sjwf50verf`, а фактический subId в таблице
`clients` (`sub_id=428cd8a14adc4c7b`) отличался. В форке 3.11 клиент живёт в
**трёх местах** (`clients`, `client_inbounds`, `inbounds.settings.clients`), и
`subId` в `settings.clients` может быть несинхронизирован. **Источник истины для
subId — таблица `clients`.** Проверять:

```
sqlite3 /etc/x-ui/x-ui.db "select id,email,sub_id from clients"
```

Причина 2 — **реальная флапающая выдача**. По фактическому subId
`subLinks` даёт 2 ссылки, но не всегда: серия из 8 вызовов — `2,2,0,2,2,2,0,2`
(~25 % пустых ответов), при этом `nodes/list` всё время показывал все ноды
online. Пустой ответ отдаётся **мгновенно** (`0.0 с`), ошибки в логе мастера нет
— похоже на гонку при сборке списка хостов (в форке ссылки собираются через
`hosts`/`client_inbounds` + данные ноды).

**Влияние на прод: нет.** Клиентский эндпоинт `https://netru.ru.net:2096/<subPath>/<sub_id>`
стабилен — 8/8 ответов `200` с 2 ссылками. Флапает только admin-API, которым
пользуются скрипты и, возможно, бот.

## 3. E2E ссылок из реальной подписки

Ссылки получены decode'ом base64-тела `2096/<subPath>/428cd8a14adc4c7b`:

* вход: `vless://…@31.77.169.67:443?security=reality&sid=cb18f0&sni=www.bing.com&fp=firefox…`
* выход: `vless://…@195.242.118.2:10001?security=tls&pcs=76145d04…6eef0&alpn=h2,http/1.1`

| Точка запуска | Вход (Reality, bing) | Выход (TLS + пин) |
|---|---|---|
| мастер (МСК), `probe_reality.py sru` | ✅ 4/4 прогона, exit `195.242.118.2` | ✅ (ранее `probe_reality.py s3`) |
| домашний ISP (AS48416), `link_probe.py` | ⚠️ нестабильно: было 3/3 дважды, затем 0/3 ×7 | ✅ 3/3 (после фикса пина) |
| мобильный клиент оператора | ✅ работает (S_RU и S3 в зависимости от сайта) | ✅ |

Вывод: связка сдана. Нестабильность входа **с домашнего ISP** — свойство
пути/точки запуска, а не сервиса: с мастера тот же вход 4/4, мобильный клиент
работает. Для мониторинга запускать probe **с мастера** (как и предписано в
§8.6c).

## 4. Баг в `servers/sru/scripts/link_probe.py` (исправлен)

Скрипт умел только Reality, а ссылка на выход S3 — `security=tls` + пин. При
добавлении поддержки TLS выяснилось:

* имя поля пина в клиентском конфиге — **`pinnedPeerCertSha256`** (top-level
  `tlsSettings`). Вариант `pinnedPeerCertificateSha256` Xray **молча игнорирует**:
  конфиг грузится, соединение падает на `x509: certificate signed by unknown
  authority`. Диагностируется только по логу `debug` — в UI/на «таймауте» не
  видно.
* `allowInsecure` в Xray 26.10.21 удалён: `The feature "allowInsecure" has been
  removed and migrated to "pinnedPeerCertSha256"(pcs) and "verifyPeerCertByName"(vcn)`.
* `fingerprint` (uTLS) надо ставить **только если есть в ссылке**. Скрипт
  подставлял `firefox` по умолчанию — для `security=tls` это лишнее.
* `serverName` при отсутствии `sni` — подставлять адрес хоста.

Итог правок: `parse()` читает `sec/pcs/alpn/sni`, `build()` собирает либо
`realitySettings`, либо `tlsSettings`; socks-порт настраивается через
`XRAY_SOCKS_PORT` (иначе повторные прогоны бьются о занятый порт и дают ложный
`0/3` — ещё одна ловушка, на которую я потратил время).

## 5. Прочие наблюдения

* Мастер каждые ~30–60 с пишет `WARNING - remote s-ru-entry / S3-EU-exit onlines
  fetch failed: context deadline exceeded`. Это **телеметрия** (сбор
  `onlines`/`lastOnline` с нод), на выдачу подписок не влияет. Аналогичные
  ошибки `getUpdates: tls handshake timed out` — сетевые таймауты Telegram с
  мастера, бот при этом работает.
* Ловушка диагностики Reality (подтверждена): `openssl s_client` с SNI, **равным**
  `target`, висит — это штатный Reality-путь; с посторонним SNI проходит
  (fallback). «TLS OK» через `openssl` ничего не доказывает — проверять
  аутентифицированным клиентом.
* `hosts` и `client_external_links` в БД мастера пусты — ссылки собираются из
  инбаундов/`client_inbounds`, это норма для установки.
