# Регламент работы ассистента (workflow для сессий OpenHands)

Эта инструкция — для агента (OpenHands / любой LLM-ассистент), работающего с репозиторием
и серверами. Оператору файл нужен как эталон: что требовать от ассистента и что считать
выполненной сессией.

Базовый принцип: **сначала факты, потом изменения. Сначала причина, потом правка.
Сначала документация, потом «готово».**

Если этот файл противоречит `AGENTS.md` — приоритет у `AGENTS.md`.

---

## 1. Окружение и точка входа (читать в начале каждой сессии)

- Клон агента: `/workspace/project` (origin = `myserver:/root/vpn-infra`).
- SSH: `ssh -F ~/.ssh_work/config myserver '<команда>'`;
  git: `GIT_SSH_COMMAND="ssh -F /home/openhands/.ssh_work/config" git pull`.
- Порядок чтения:
  1. `AGENTS.md` — соглашения и жёсткие правила репозитория
  2. `docs/session-start.md` — чеклист старта
  3. `docs/system-state.md` — текущее состояние системы
  4. `docs/next-session-todo.md` — источник истины по открытым задачам
  5. Свежие `docs/checkpoint-*.md` (по датам)
- Известные грабли живых сервисов (subLinks-флап, источник `subId`, пин-поля Xray,
  консистентность БД ноды) записаны в `AGENTS.md` — перечитывать каждый раз,
  полагаться на память нельзя.

## 2. Живые серверы — жёсткие правила

- S1, S2, S3, S_RU и Panel — **продакшн**.
- Диагностика — только read-only команды, по возможности из `docs/diagnostic-commands.md`.
- **Любое изменение на живом сервере — только после явного запроса/одобрения оператора**
  в текущей сессии. Сначала предложить точную команду/правку, дождаться подтверждения.
- Не пушить в основную ветку на сервере: изменения доставляются через отдельную
  рабочую ветку (см. §9).
- `secrets/` зашифрован git-crypt. Не читать, не расшифровывать, не выводить содержимое,
  не коммитить расшифрованные копии.

## 3. Языковая политика

- Разговор с оператором: русский.
- Markdown-доки и коммиты: русский (конвенция репо).
- Код, конфиги, комментарии: на языке конкретного файла (код бота — English),
  не переключать язык внутри файла.
- Не переводить существующие файлы «заодно» с другой задачей.

## 4. Общие принципы работы

**Ничего не менять, пока:**
1. Не прочитаны все относящиеся к задаче части (код, конфиги, состояние живой системы, логи);
2. Поведение подтверждено фактами, а не предположениями;
3. Установлена причина (root cause), а не только симптом.

**Не выдумывать и не подставлять наугад:**
- адреса, порты, пути;
- схемы БД и содержимое таблиц;
- ключи конфигов, имена токенов, настройки панелей;
- поведение скриптов, описанное в доках.

Нет данных — предложить точную read-only команду для проверки, а не догадку.

## 5. Формат ответа

Каждый ответ делится на две явные части.

**Часть 1 — Предположения**
- без команд и кода;
- выводы и гипотезы из уже собранных данных;
- явно перечислить, что ещё неизвестно.

**Часть 2 — Команды / запросы**
- минимальный набор команд для подтверждения/опровержения предположений;
- сначала read-only; изменяющие команды — только после явного одобрения оператора
  и установленного root cause, приводить их отдельной цитатой;
- держать батч небольшим, выводы вставлять в анализ следующего шага.

**Каждый ответ заканчивается строкой:**
```
context: ~<N> tokens
```
Если сессия подходит к заметной длине — не начинать крупную новую работу,
а создать/обновить чекпоинт (§8).

## 6. Порядок расследования

1. **Доки** — `system-state.md`, свежий чекпоинт, профильные `servers/<name>/...`;
2. **Состояние процессов/логов** на сервере — по SSH, read-only;
3. **Живой статус** — health-эндпоинты, состояние панелей, трафик-пробы;
4. **Персистентное состояние** — БД/конфиги (например, sqlite3 x-ui.db, bin/config.json);
5. **Исходники в репо** — реальные скрипты и конфиги в `servers/`.
Доку в репо — доверять как гипотезе: при расхождении с живым состоянием
источник истины — живая система.

## 7. Правки кода и конфигов

Перед правкой:
1. Искать в репо готовый механизм — скрипт, чеклист или доку, уже решающую задачу;
2. Смотреть, как та же задача решена на других серверах (`s1`, `s2`, `s3`, `sru`);
3. Прочитать актуальное содержимое файла на сервере перед правкой его клона;
4. Только после этого проектировать изменение.

Не вводить новые инструменты/паттерны «заодно»: следовать стилю репо
(баш-скрипты на сервер в `servers/<name>/scripts/`, доки в соответствующие подкаталоги).

**Способ правки:** файлы редактируются в клоне агента, минимальными точечными правками,
затем коммит и (по одобрению оператора) доставка на сервер через ветку. На живом сервере
не делать ad-hoc правок мимо репозитория.

## 8. Чекпоинты длинных сессий

Для многошаговых расследований — один активный чекпоинт на тему:
- подтверждённые факты (со ссылкой на команду/вывод);
- открытые вопросы;
- принятые и отложенные решения;
- точный следующий шаг.

Обновлять на вехах или в середине длинной сессии. Чекпоинты не удалять: если вывод
поменялся — добавить корректирующий чекпоинт по новой дате, историю не переписывать.

## 9. Архитектурные изменения

Всё, что затрагивает несколько файлов, серверов или меняет схему (туннели, порядок
outbound, регистрацию нод), проходит через:

```
Проблема → Факты → Причина → Варианты → Решение (записанное) → Правка
```

- «Варианты» не пропускать даже когда кажется очевидным;
- решение фиксируется в чекпоинте сессии; сводка — в `system-state.md`;
  если грабли пригодятся следующим сессиям — короткое дополнение в `AGENTS.md`.

## 10. Документирование (по реальной структуре репо)

Не изобретать новую иерархию доков — использовать существующую:
- точка входа: `AGENTS.md`, `docs/session-start.md`;
- живой статус: `docs/system-state.md`;
- открытые задачи: `docs/next-session-todo.md`;
- темы: `docs/commercial/`, `docs/home/`, `docs/shared/`, `servers/<name>/`;
- история: `docs/checkpoint-*.md`, `docs/commercial/operations-log.md`.

**Single source of truth:** каждый факт записан ровно один раз, остальные места ссылаются.
При изменении картины приоритетов обновлять `session-start.md` (раздел 5) и
`next-session-todo.md` — это входные точки оператора.

## 11. Сессия = чекпоинт

Сессия не считается завершённой без шага документации:

1. Создать `docs/checkpoint-YYYY-MM-DD-<тема>.md`: подтверждённые факты (с уликами
   — командами/выводами), решения, открытые вопросы, точный следующий шаг;
2. Обновить `docs/system-state.md` (что изменилось в системе);
3. Обновить `docs/next-session-todo.md` (закрыть выполненное, добавить новое);
4. Обновить затронутые тематические доки (`servers/<name>/...`, `commercial/...`);
5. Закоммитить всё (§12).

## 12. Гигиена коммитов

- Сообщения коммитов — по-русски с префиксом области (`docs:`, `bot:`, `s3:`, `sru:` …);
- Группировать коммиты по темам, а не по сессиям;
- `secrets/` в расшифрованном виде не коммитить никогда;
- Если пришлось остановиться до коммита — явно отметить это в чекпоинте.

### Правило «откат без подтверждения» (после аварии S1 31.10.2026)

Авария: `route 0.0.0.0 0.0.0.0` в серверном конфиге OpenVPN на S1 увёл весь egress
в туннель, внешний SSH умер, доступ остался только через консоль провайдера.

Чтобы это не повторилось, любое **рискованное** изменение сетевого/маршрутного
поведения на живом сервере вводится по схеме «окно на подтверждение»:

1. **Автозагрузка не запрещается.** Требование «не добавлять в автозагрузку» —
   ловушка: сервер не вернётся после ребута (на S1 это проверено 31.10.2026).
   Вместо запрета автозапуска ставится сторож, который откатывает небезопасное
   состояние.
2. **Сторож с таймером.** Перед применением правки взводится сторож
   (`openvpn-guard.sh revoke`): пока оператор не выполнил `openvpn-guard.sh confirm`,
   таймер (60 с) проверяет главную таблицу маршрутов и снимает маршруты-угона
   (`0.0.0.0/1`, `128.0.0.0/1`). Три срабатывания подряд — сторож останавливает
   подозрительный юнит (`openvpn-server@home-s3`).
3. **Подтверждение — явное действие оператора**, а не «всё ещё работает». Успешный
   ping или SSH после правки подтверждением НЕ считается: при утечке маршрута
   подключение может держаться на уже установленной сессии.
4. **Реализация:** `servers/s1/scripts/openvpn-guard.sh`,
   `servers/s1/systemd/openvpn-guard.{service,timer}`, состояние в
   `/etc/openvpn-guard/`, лог `/var/log/openvpn-guard.log`.
5. **Область действия.** Правило обязательно для правок, способных увести egress
   (`route`, `redirect-gateway`, `ip rule`, таблицы маршрутизации, NAT). Для правок,
   не влияющих на путь до сервера, сторож не требуется.
6. **Полный ребут** — обязательная проверка после сетевой правки: только он
   показывает, что автозапуск и персистентность согласованы.

## 13. Definition of Done

Сессия/изменение завершены, только когда:
- [ ] причина подтверждена уликами, а не догадкой;
- [ ] изменения доставлены согласованным способом (ветка → проверка → одобрение оператора);
- [ ] живые изменения проверены (статус сервиса, логи, E2E-проба по необходимости);
- [ ] документация обновлена (§11);
- [ ] соседнее поведение не задето (смежные туннели, бот, подписки);
- [ ] для сетевых правок — сторож `openvpn-guard` взведён/подтверждён (§12) и ребут проверен;
- [ ] `git status` в клоне чист — всё закоммичено;
- [ ] push/деплой — только туда, куда попросил оператор.

## 14. Самопроверка перед завершением

Перед тем как объявить сессию выполненной, пройтись по регламенту: формат ответа (§5),
порядок расследования (§6), согласие на изменения живых серверов (§2), секреты (§2),
документация (§10–11), Definition of Done (§13), гигиена коммитов (§12).
Незакрытый пункт — либо доделать, либо явно зафиксировать разрыв в
`next-session-todo.md` перед остановкой.
