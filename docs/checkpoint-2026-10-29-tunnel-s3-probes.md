## Диагностика туннеля S1 ↔ S3 (read-only, зонды)

Состояние: сервер S3 `openvpn[24173]` (unit `openvpn-server@home-backup`) слушает
8443/TCP; клиенты циклически переподключаются. Из настроек сервера: `dev tun`,
`topology subnet`, `server 10.10.0.0/24`, `data-ciphers AES-256-GCM`, `tun-mtu 1300`,
**`proto tcp` без `port`… `port 8443`, keepalive 10/60**. Директив
`management`/`mtu-disc`/`fragment`/`mssfix` в конфиге нет.

Пакетные пробы (TCP-connect до 195.242.118.2:8443 → пауза 0.2 с → одна запись N
байт 'A' → ожидание ответа до 20 с). Места запуска: S1 (194.55.236.229) и
локально на S3 (195.242.118.2). Сопоставление с журналом
`openvpn-server@home-backup` (окно ±40 с). Итог за ~30 зондов:

| N | Откуда | Реакция S3 (журнал) |
|---|--------|----------------------|
| ≤1768 (вкл. 100, 140, 1768) | S1 и S3a | сеанс живёт: TLS ok, `[s1] Peer Connection Initiated`, `Data Channel AES-256-GCM`, reset'ов нет; зонд молчит (ожидаемо: это не OpenVPN-пакет) |
| 200 (только первый раз) | S1 | короткое эхо 24 байта |
| ≥250 (250–2500) | S1 и S3a | `WARNING: Bad encapsulated packet length from peer (16705), … <= 1768` → `Connection reset, restarting [0]` |

Устойчивые наблюдения:

1. **«Только 200-байтный зонд получил эхо, и он же был первым.** Повторы 200 B
   (S1, 2 прогона) и поздний контроль 5000 B на том же сеансе — тишина.
   Аномалия разовая, в таблицу вынесена для честности протокола.
2. Порог ровно по границе из предупреждения: ≤1768 — сеанс жив, ≥250 —
   `Bad encapsulated packet length (16705)` и reset. Сеанс 51182/52930 жил
   минуты после записи ≥250 B (в буфере сокета 42–210 байт), kill случался
   при следующей активности на сокете.
3. Рост N (до 2500) не меняет картину (16705 ≠ N; переполнения нет) и не
   отключает сессию немедленно.

Прежняя сессия (до 29.10 23:55 МСК): ping 10.10.0.1 ↔ 10.10.0.2 — 100% loss;
tcpdump на tun2 (S3) видел ICMP от 10.10.0.2 без ответов; обратное направление
— 0 пакетов.

## Гипотеза (для следующей сессии, не подтверждена)

Признак «Bad encapsulated packet length (16705)» = конкретное число (0x4141,
`41 41`) как старшие байты псевдодлины: сервер читает 2 байта длины со сдвигом
на 1 байт от реального начала записи (например, 0x01 0x41 от нашего `01 41 41…`
при N=300+), т.е. поток байтов, приходящий серверу, **сдвинут на константу**.
Стабильность при N=250–2500 исключает переполнение длины; совпадение границы
1768 — совпадение, а не согласование MTU (16705 > 1768 всегда).

- Высокий приоритет: воспроизвести `Bad encapsulated` на **loopback S3**
  (`openvpn --config server --proto tcp --port <тестпорт>` + raw-клиент,
  повторяющий зонд): воспроизведётся — баг OpenVPN (26.x?) в обработке
  первого пакета; не воспроизведётся — внесетевые искажения/накладка.
  Сравнить при одинаковом состоянии соединения (новый connect / переиспользование).
- Средний: рассмотреть смену proto на udp (если сеть позволяет) —
  другой парсер длины, иной профиль сбоя;
- Средний: `tcpdump` на S3 на шифротрафик при заведомо плохом пакете
  (длина, приходящая по сети, vs длина, которую увидел OpenVPN);
- Низкий: `mtu-disc yes` (PMTU, TCP — ignore-dfw), `port-share` для
  идентификации немодифицированных байтов.

Не решено (из прошлой сессии): дубликат 10.10.0.2 (s1 и `ovpn-s3-backup`),
конфликтный максимумовский конфиг; вяло текущий tun2 (RX ~192 B, TX ~4.3 KB).
