# Чекпоинт 2026-10-30 — S1↔S3: проверена инверсия направления, туннель S3→S1 РАБОТАЕТ

## Контекст

Прямое направление (S1-клиент → S3-сервер 8443/TCP, прод-конфиг `home-backup`) стабильно умирает
на 61-й секунде: handshake/PUSH_REPLY проходят, дальше data-пакеты не подтверждаются — обе стороны
рвут по `--ping-restart`. Ранее (см. `checkpoint-2026-10-30-tunnel-s3-shift-refuted.md`) гипотеза
«сдвиг байтов» опровергнута, матрица тестов показала port/transport-независимость симптома для OpenVPN.

## Эксперимент (30.10, ~13:32–13:42 МСК)

По предложению оператора проверили **инверсию роли**: тестовый сервер подняли на S1, клиент — на S3.
- Одноразовый PKI (`VPNDIAG-TEST-CA`, срок 3 дня) в `/tmp`, прод-ключи и серты не использовались;
- Прод-порт 8443/TCP и прод-шифр AES-256-GCM сохранены — отличие только в направлении;
- Первая попытка упала на ключе `certificate does not have key usage` — тестовая ЦС выпускала серты
  без X.509-расширений; перевыпуск с keyUsage/EKU устранил;
- tls-auth на прод-сервере S3 (файл `tls-crypt-home.key` в server.conf) — не при чём: тест жил и так.

## Результат

- TLS-хендшейк, PUSH_REPLY, Data Channel — оба направления;
- Ping через туннель: **S1→10.77.0.2: 15/15 (0%), S3→10.77.0.1: 12/12 (0%)** — в прямом направлении
  в это же время 100% потерь;
- Устойчивость: сессия прожила 4+ минуты без единого флапа (прямая умирает на ~61 с);
- Объём: 3.6 МБ S3→S1 без потерь, ~0.7 МБ/с;
- MTU 1150 B через туннель — 10/10 (0%).

## Вывод

**Блокировка DPI-класса асимметрична по направлению инициирования TCP-соединения:**
- S1→S3 (SYN от S1) — не устанавливается даже plain TCP;
- S3→S1 (SYN от S3) — plain TCP проходит, но OpenVPN-данные в прямом направлении дропаются после handshake;
- При **обратной роли** (сервер S1, клиент S3) OpenVPN-трафик живёт стабильно.
Профиль согласуется с выборочной DPI-манипуляцией (TSPU): соединения, инициированные S1 (ДЦ maximum.ru.net),
подвергаются обработке, инициированные S3 — нет. Для надёжного вывода нужен тест с нейтрального VPS,
но практический вывод уже есть: **рабочий вариант S1↔S3 существует — S3 должен быть клиентом, S1 — сервером.**

## Рекомендация

Перевести связку S1↔S3 на сервер-S1/клиент-S3 (конфиг-зеркало прод-параметров: 8443/TCP, AES-256-GCM,
tls-auth/tls-crypt `tls-crypt-home.key`, tun-mtu 1300, keepalive 10 60). Изменение затрагивает только
резервный канал, прод (коммерческий exit через S3:10001, бот через 38417) не затрагивается. Изменения применяются
только по явному запросу оператора (правило read-only сессии).

## Изменения в инфраструктуре

Тестовый стенд (`/tmp/vpntest` на обеих сторонах, PKI на 3 дня) остановлен и удалён; прод-сервисы не тронуты:
на S1 работают `server` (10.9.0.1), `s2-client` (tun0), `s3-backup` (tun2); на S3 — `home-backup` и `sru-transport`.
